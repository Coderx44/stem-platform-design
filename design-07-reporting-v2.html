Section 7: Reporting & Analytics — Two Approaches

Approach A: Traditional dashboards with materialized views — Approach B: AI-powered natural language query engine

Decision pending: Both approaches are viable and can coexist. Review trade-offs below — we'll finalize which to prioritize (or combine) later.

Approach A: Traditional Dashboards + Materialized Views

Pre-built dashboards, scheduled aggregation, structured export

Architecture
Data Sources
Attendance, assessments, sessions, rubrics, leave — all tenant-scoped via RLS
Aggregation
Materialized views pre-compute metrics. Cron refreshes nightly.
Report Engine
Role scoping, date filters, group-by. Feeds dashboard API.
Output
Charts, tables, PDF reports, Excel downloads

Pros

  • Predictable, consistent output — same dashboard every time
  • Fast loads (pre-computed materialized views)
  • No LLM cost per query
  • Easy to test and validate correctness
  • Works without internet (cached dashboards on mobile)
  • Familiar UX for NGO staff

Cons

  • Every new report = new dev work (design, query, UI)
  • Can't answer ad-hoc questions
  • Heavy upfront build — 10 dashboards is significant frontend effort
  • Data up to 24hrs stale (mat. view refresh cycle)
  • Users stuck with what's built — no self-service

Approach B: AI-Powered Natural Language Query Engine

Users ask questions in plain English → system generates SQL → returns charts & tables. Based on KindKart's proven NL query system.

Architecture (Proven in KindKart)
1. User Query
"Show me trainer utilization for last month"
→
2. Schema Context
Keyword match → load relevant domain schema docs
→
3. LLM Call
Schema + query → SQL + chart type + columns
→
4. Validate SQL
Table whitelist, no DML, no params, no injection
→
5. Execute & Render
Run SQL, return chart (table/bar/line/pie/kpi)
Key Components
Schema Docs (Embedded)
Markdown files per domain:
- Table names, column types
- Join relationships
- Common query patterns
- Enum values, status codes
- Compiled into binary at build

Keyword routing: "trainer", "utilization" → loads trainer + attendance schema docs
SQL Validator (Security)
Before execution, validate:
- Table whitelist (40+ allowed)
- Block sensitive tables (auth, tokens)
- No INSERT/UPDATE/DELETE/DROP
- No positional parameters ($1)
- No hardcoded strings in SELECT
- Inject tenant_id WHERE clause

Jailbreak prevention built-in
Chart Renderer
LLM returns chart metadata:
- chartType: table/bar/line/pie/kpi/gauge
- column definitions (key, label, type)
- Row data as arrays
- Chart name

Frontend renders using chart library.
Results persisted → reusable dashboards.
Multi-Tenant Adaptations for STEM
Tenant Isolation in NL Queries
- Every generated SQL gets tenant_id = ? injected automatically
- RLS provides second layer of protection
- Role-based query scoping: Trainers can only query their own data, PMs their cluster, Donors their assigned schools
- Table whitelist is tenant-configurable (based on licensed modules)
Module-Aware Schema Loading
- Schema docs only loaded for modules the tenant has licensed
- If tenant doesn't have Assessment module, LLM never sees assessment tables
- Prevents queries about unlicensed features
- Reduces prompt size → faster, cheaper LLM calls
Example Queries Users Can Ask:
"Show attendance rate by school for March 2026"
"Which trainers have logged less than 3 days this week?"
"Compare baseline vs endline scores for Grade 5 science"
"Top 5 schools by student improvement percentage"
"Monthly leave breakdown for all trainers in Cluster A"
"RAG status of all schools with donor XYZ"

Pros

  • Self-service — users get answers without dev work
  • Infinite report variety from day one
  • Proven architecture (running in KindKart production)
  • Dramatically less frontend work — one query UI, one chart renderer
  • Handles ad-hoc questions that pre-built dashboards can't
  • Schema docs double as documentation
  • Module-aware: only shows data for licensed modules

Cons

  • LLM cost per query (API calls to AI service)
  • Response latency (2-5s per query vs instant dashboard)
  • Non-deterministic — same question may produce slightly different SQL
  • Requires good schema docs for accurate results
  • Complex queries may produce incorrect SQL
  • Requires internet (can't work offline)
  • Security surface area (SQL injection via LLM — mitigated by validator)

Possible Hybrid: A + B Combined

Core dashboards (Approach A)
Build 3-5 critical dashboards as traditional views:
- Trainer daily view (attendance status)
- PM approval queue
- School RAG overview
- Student attendance summary

These are high-frequency, must-be-fast, must-work-offline views.
Everything else (Approach B)
AI query engine for everything else:
- Ad-hoc analysis by PM/Admin
- Donor impact reports (custom)
- Year-over-year comparisons
- Any question not covered by core dashboards

Users save useful queries as pinned "dashboards" for reuse.
Hybrid benefit: You build fewer traditional dashboards (3-5 instead of 10+), while the AI engine covers the long tail of reporting needs. Users get instant access to critical views AND self-service analytics. Best of both worlds.
