  USING (tenant_id = current_setting('app.tenant_id')::uuid)

Key Database Design Decisions

tenant_id on EVERY table
Even if it's derivable via joins. Enables simple RLS policies, avoids cross-table joins for security checks. Slight denormalization, massive security win.

Pro

  • RLS policy is one line per table
  • No accidental cross-tenant joins

Con

  • Redundant column on child tables
JSONB for flexible fields
Assessment scores, audit trails, tenant config overrides, and notification preferences use JSONB. Allows per-tenant customization without schema changes.

Pro

  • Flexible per-tenant config
  • No migrations for new fields

Con

  • No schema enforcement on JSONB
  • Validate at app layer
Composite indexes for performance
All frequently queried tables get (tenant_id, ...) composite indexes. E.g., (tenant_id, trainer_id, date) on attendance for daily lookups.

Pro

  • Fast tenant-scoped queries
  • RLS filter is index-backed

Con

  • More indexes = slower writes
Soft deletes everywhere
All entities use deleted_at timestamp instead of hard deletes. Required for audit compliance and data recovery. RLS policies filter out deleted rows by default.

Pro

  • Full audit trail
  • Easy data recovery

Con

  • Table bloat over time
  • Must filter in every query
