Access Control Implementation

3 Layers of Access Control
Layer 1 — RLS (DB): Tenant isolation. No cross-tenant access possible.
Layer 2 — Module Gating (Middleware): Licensed modules only. 403 if not licensed.
Layer 3 — Role Permissions (Controller): Action-level checks. Role must have permission for specific operation.
Data Scoping
Trainer: Sees only their assigned schools + own data
Project Manager: Sees all trainers + schools in their cluster
Donor: Sees only their assigned/funded schools
Admin: Sees everything within the tenant

Per-Tenant Permission Overrides

Role types are system-defined, but permissions are configurable per tenant

── Data Model ──
permissions
id, key, module_id, description
e.g. "mark_attendance", "approve_entries", "create_session", "view_reports"
role_default_permissions
role, permission_id, granted
System-wide defaults. Works out of the box for new tenants.
tenant_role_overrides
tenant_id, role, permission_id, granted
Sparse — only stores exceptions to defaults.
── Example: Two Tenants, Same Role, Different Permissions ──
Tenant A — "NGO Alpha" (uses defaults)
Trainer can: mark attendance ✓, create sessions ✓, upload students ✓
(No overrides — system defaults apply)
Tenant B — "NGO Beta" (custom overrides)
Trainer can: mark attendance ✓, create sessions ✗, upload students ✗
(2 overrides in tenant_role_overrides)
Why this approach: Roles are system-defined (Trainer, PM, Donor, Admin) — tenants don't create custom role types. But each tenant can toggle specific permissions on/off per role. The tenant_role_overrides table is sparse (only stores exceptions), keeping it simple. New tenants work out of the box with system defaults. Admin configures overrides via a settings UI.
