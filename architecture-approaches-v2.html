Architecture Approaches

Three approaches for the STEM platform — evaluate trade-offs and pick a direction

A

API-First Modular Monolith

Single backend service with internal module boundaries. Next.js and React Native both consume the same REST/GraphQL API. Modules are npm packages within a monorepo.

Pros

  • Simplest to deploy and operate (one service)
  • Shared types across modules — easy refactoring
  • Fast inter-module calls (in-process)
  • Single CI/CD pipeline
  • Perfect for small-medium team (5-15 devs)
  • S3 gives full control over file lifecycle and CDN

Cons

  • All modules scale together (can't scale assessment independently)
  • One bad module can crash everything
  • Requires discipline to maintain module boundaries
  • Deployment = full app redeploy
  • Must build/manage auth yourself
B

Supabase-Native with Edge Functions + S3

Lean heavily on Supabase for auth, DB, and realtime. Use Edge Functions (Deno) for business logic. S3 for all media/file storage (OMR sheets, documents, photos).

Pros

  • Least custom code — Supabase handles auth, DB, realtime
  • Auto-generated REST/GraphQL from DB schema (PostgREST)
  • Fast to prototype and ship MVP
  • S3 gives scalable, cheap media storage with presigned URLs

Cons

  • Edge Functions have cold-start latency + execution limits
  • Complex business logic (workflows) awkward in Edge Functions
  • OMR processing must be a separate service anyway (can't run in Edge Functions)
  • Vendor lock-in to Supabase platform
  • Hard to maintain modular boundaries
  • Testing Edge Functions is less mature
C

Hybrid: Modular Backend + Supabase Auth/DB + S3

Custom TypeScript backend for all business logic (modular monolith). Supabase for Auth and PostgreSQL. S3 for all media/file storage. Clean separation of concerns.

Pros

  • Full control over business logic + clean module boundaries
  • Supabase handles what it's best at (auth, JWT, RLS, PostgreSQL)
  • S3 gives scalable, cheap storage with presigned URLs + CDN
  • OMR processing runs in proper compute (no function limits)
  • Fully testable — standard TypeScript, standard test frameworks
  • Can migrate off Supabase or S3 independently if needed
  • Team writes TypeScript everywhere

Cons

  • More infrastructure than pure Supabase (need to host backend)
  • Two auth integration points (Supabase JWT validated in backend)
  • Slightly more initial setup than Approach B

Recommendation: Approach C (Hybrid)

Approach C gives you the clean modular boundaries of A, the managed-service benefits of B, and avoids the limitations of both. Your OMR processing, workflow engine, and reporting modules need real compute — not Edge Function constraints. Supabase handles identity + database, S3 handles all media, and your TypeScript backend owns all business logic. Three services, each doing what it does best.
